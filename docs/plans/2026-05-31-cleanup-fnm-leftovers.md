# Clean up fnm leftovers after node-archive migration

## Overview

The Node runtime was migrated from the `fnm` manager-binary acquisition to a
direct, SHA-256-pinned archive (see the prior migration; clean break, `fnm`
runtime kind removed). The migration left scattered `fnm` references in code
comments, test fixtures, a dedicated migration guide, and the completed plan.

**Goal:** zero occurrences of `fnm` in the tracked source tree (except
false-positive hash substrings), per the user's "всё до нуля" decision.

This is a cleanup change — no behavior changes. Verification is a green
`go build` + `go test ./...` + linter, and `rg -i fnm` returning nothing across
the tracked tree (minus the documented false-positive exclusions).

### Scope decisions (locked in planning)

- **Depth:** maximal — "всё до нуля упоминаний". Touch docs, code comments, the
  clean-break tests, and the detector scoring example.
- **Completed migration plan:** **delete the file** (`git rm`). History stays in
  the git log; a redacted-beyond-recognition plan is worse than removing it.
- **Testing approach:** Regular (edit → run existing suite + scoped grep).

### What is NOT touched (documented false positives)

These contain `fnm` only as a substring inside base64 / SHA hashes — leaving them
is correct, editing them would corrupt data:

- `pnpm-lock.yaml` — `sha512-…fnm…` integrity substrings (9 hits)
- `go.sum` — base64 module-hash substring (1 hit)
- `internal/nodekeys/node_release_keys.asc` — GPG key block base64 (3 hits)
- `website/build/**` — git-ignored Docusaurus build artifacts (regenerated by
  `pnpm build`; never committed). The deployed site keeps stale `fnm` text until
  the next rebuild + redeploy — see Post-Completion.
