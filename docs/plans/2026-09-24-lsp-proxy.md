> **Why this exists.** `lsp` has been a reserved top-level key since the WASM parser work. It loads,
> it is structurally validated, and nothing reads it. Meanwhile a repository that pins every linter
> and formatter to a SHA-256 leaves its language servers — gopls, rust-analyzer,
> typescript-language-server, basedpyright, taplo, yaml-language-server — to whatever each machine
> happens to have. This plan decides what the `proxy` half of the entity does: how a server
> declared in the datamitsu config reaches an editor, what datamitsu adds on the way, and what it
> deliberately leaves to the editor. The shipped shape is the starting point: an app reference, its
> own `projectTypes`, no globs field, its own `order`.

---

## 0. The idea in one paragraph

A `proxy` entry names an app, the arguments that start it as a language server, the languages it
serves and the project types it applies to. datamitsu does not merge servers into one connection.
`datamitsu lsp servers --json` says which declared servers apply to a repository root and how to
install and start each one. `datamitsu lsp run <name>` starts one of them: load the config, install
the app the way every app is installed — hash-verified, lazily, progress as JSON-L on stderr and
nothing on stdout — then become the server. The editors datamitsu targets already run several
language clients side by side, so each runs one client per listed server. The one conflict
datamitsu must own is formatting: a proxied server offers no formatting of any kind, because the
formatter of record is `datamitsu fix`. The VS Code extension applies that rule, and the config's
server settings, in its own clients. For every other editor a thin one-to-one relay inside
`lsp run` applies them; it is a later stage. A multiplexer that merges several servers into one
connection is not planned.

### 1.1 The shipped entity is a declaration with dangling references

- `LspEntry{Type, App, ProjectTypes, Tool, Order}` flattens the `proxy`/`derived` union
  (`internal/config/config.go:396-421`). The top-level field is `Lsp MapOfLsp` with `omitempty`
  (`:538-540`).
- `ValidateLsp` (`internal/config/validate.go:617-668`) checks only that a proxy has a non-empty
  `app` and a non-empty `projectTypes`. Three things are not checked:
  - that `app` exists in `apps`, although `config/config.d.ts:613-617` documents it as "Name of the
    app (in `apps`)";
  - that each `projectTypes` name is a declared project type;
  - that a proxy carries no `tool` and a derived entry no `app`. Both are accepted silently.
- The validator runs in the loader (`cmd/config_loader.go:522`), and the validated config is what
  the config-eval cache stores (`:531-537`).
- Tool `projectTypes` names are not validated either. An unknown name simply never matches
  (`internal/tooling/planner.go:788-805`). `docs/backlog/` has no item for it.
- Nothing reads `Config.Lsp` outside validation. `lessLspByOrderThenName` (`config.go:434-444`:
  `order` ascending, ties by entry name) is used only by `internal/config/tool_facet_test.go:80-118`.
- The published example is `"go-lsp": { type: "proxy", app: "gopls", projectTypes: ["golang"] }`
  (`website/docs/reference/configuration-api.md:1680`). No shipped config defines a project type
  named `golang`: the embedded default config defines no project types, and the pinned wrapper
  (`0.0.0-unstable.20260912.f201136`) calls its Go type `golang-package`.
- An app carries no default arguments, except a shell app's `args`
  (`internal/binmanager/binmanager.go:109-113`), and a Node or Bun app runs exactly one `binPath`
  (`:73-90`). So `ruff server`, `tombi lsp` or `typescript-language-server --stdio` cannot be
  expressed by an app reference alone.

### 1.2 The entity sits inside the execution-cache key

- `calculateInvalidationKey` hashes the version, `json.Marshal` of the **whole** `config.Config`,
  and the selected tools (`internal/cache/cache.go:579-607`). Any edit to an `lsp` entry therefore
  resets every tool's cache for every user, although no entry can change a verdict.
- The field is `omitempty`, and neither the embedded default config nor the pinned wrapper declares
  an entry. Clearing the field before hashing therefore moves no existing key.
- The config file itself is a file the repository's own lint and fix operations cover. Editing an
  entry also changes that file's content hash, so its per-file entries and the verdict of the unit
  that contains it miss (`cache.go:407-468`), whatever the invalidation key does.
- The config-eval cache stores `Lsp` too. Its `FormatVersion` is 4 and must be bumped whenever the
  encoded shape changes (`internal/configcache/key.go:25-28`).
- The diagnostics plan recommends removing `derived` (its D6, Stage 4), because diagnostics derive
  implicitly from lint operations; the cache reset above is a reason this plan adds, not that one.

### 1.3 The formatting server cannot carry another server's traffic

- It is single-threaded (`internal/lsp/server.go:30-33`). It dispatches only lifecycle messages,
  full-text sync and `textDocument/formatting` (`:573-601`).
- The inbound `message` has no `result` or `error` field (`internal/lsp/protocol.go:47-52`), and
  `isRequest` means "has an id" (`:55`). A client's response to a server-initiated request would be
  answered with MethodNotFound, so the server cannot issue a request to the client at all.
- `textDocumentItem` keeps only `uri` and `text` (`protocol.go:186-189`). The `languageId` and
  `version` a child server needs are discarded on decode.
- Its capabilities are hard-coded: `positionEncoding: "utf-16"`, full sync,
  `documentFormattingProvider: true` (`server.go:624-639`).

### 1.4 How an app is launched today

**`datamitsu exec`**

- `datamitsu exec <app> [args]` loads the config, resolves the command and runs it as a **child**
  with the parent's stdio (`cmd/exec.go:121-170`; `internal/binmanager/binmanager.go:915-944`).
- The parent stays alive for the child's whole lifetime and installs no signal handler: the command
  context is a background context (`cmd/root.go:37-44`).
- Any failure, including the child's own non-zero exit, becomes exit 1 (`cmd/exec.go:37-40`).

**Where install progress and config output go**

- On a cold store, when stdout is not a terminal, `exec` writes install progress to **stdout**:
  - `ui.New` binds `out` to `os.Stdout` (`internal/ui/ui.go:85-86`), and `Statusf` writes to it
    (`:102-104`);
  - the plain spinner (`internal/ui/spinner.go:93`) and the plain download reporter
    (`internal/ui/download.go:279`) both go through `Statusf`;
  - only JSON-L quiet mode drops those lines (`ui.go:172`).
- Outside quiet mode a config's `console.log` prints to stdout too
  (`internal/engine/console.go:34-38`). `runLsp` relies on quiet mode for exactly that
  (`cmd/lsp.go:61-63`).
- An editor that spawned `datamitsu exec gopls` on a fresh machine would therefore receive progress
  text as the first bytes of the LSP stream.
- `datamitsu lsp` forces JSON-L quiet mode through `PersistentPreRun` (`cmd/lsp.go:39-40`). Cobra
  runs that hook for subcommands too, unless a subcommand defines its own.

**What the source-mode shim has that a launcher needs**

- `execProcess` calls `syscall.Exec` on Unix, so the signals, stdio and exit code are the target's
  (`internal/shim/exec_unix.go:17-24`). On Windows it runs a child with inherited stdio and adopts
  its exit code, with no job object (`exec_windows.go:16-41`). The function is unexported; the
  dispatcher reaches it through its `Exec` field (`shim.go:124`), which is also how tests stub it.
- `syscall.Exec` does not search `PATH`, so a bare command — a shell app, a system-mode `java` — is
  resolved by `lookPathOutsideFarm` first (`shim.go:937-946`). argv[0] is chosen by `execArgv0`
  (`:983-996`).
- A first-use install is spawned as a child datamitsu with stdout redirected to stderr and stdin
  closed (`shim.go:1294-1320`). That child replays the farm's recorded flags through `spawnArgs`
  (`:1177-1188`).
- The flags of the current invocation are turned into an absolute argv fragment by
  `configChainArgs` (`cmd/source.go:453-466`). Neither function carries `--binary-command` or
  `DATAMITSU_PACKAGE_NAME`, both of which the npm wrapper injects (`bin/datamitsu.js` of
  `@shibanet0/datamitsu-config`). Both are config-eval cache inputs, as `facts().binaryCommand` and
  as part of the environment.
- An editor started from a source-activated shell already finds every declared non-shell app on
  `PATH`, pinned (`internal/sourcefarm/plan.go:10-17`). It gets no entry arguments, no language list
  and no applicability, though, and it depends on the shell having been activated.

### 1.5 Provisioning

- `datamitsu init` installs (`cmd/init.go:599-702`, `internal/binmanager/dependencies.go:52-60`):
  - binary apps marked `required`, or every binary app under `--all`;
  - runtime-managed apps that declare `links` and are referenced by a tool operation
    (`filterAppsForSmartInit`), plus runtime link apps not marked `lazy`;
  - the `dependsOn` closure of those.
- So `init` does not install a binary tool app such as ruff or tombi either, unless it is
  `required`: it installs on the first `lint` or `fix`, through `EnsureTools`. An app referenced only
  by an `lsp` entry is installed on first use the same way.
- `init` runs in CI: the `setup-datamitsu` action runs it by default
  (`packaging/action/action.yml:11-14`, `packaging/action/src/main.ts:56-58`).
- `dockerfile.BuildPlan` includes every app, "matching the `init --all` semantics"
  (`internal/dockerfile/plan.go:152-156`). The generated images and the store bundles built from
  them follow.
- A Go app runs with no runtime environment (`internal/runtimemanager/go.go:399-416`). A gopls app
  would drive whatever `go` is on the inherited `PATH`.

### 1.7 The editor side

- **The VS Code extension on `main`** runs one client:
  - it spawns `datamitsu lsp` itself, with `cwd` set to the first workspace folder, and keeps the
    process's stderr for `JsonlProgress` (`editors/vscode/src/extension.ts:108-150`);
  - it disables the client's own restart, `maxRestartCount: 0` (`:180`);
  - it selects `[{scheme: "file"}]` (`:181`).
- **Workspace trust.** The extension declares `untrustedWorkspaces.supported: false`
  (`editors/vscode/package.json:129-132`), so it does not run in an untrusted workspace.
- **vscode-languageclient 10.1.1:**
  - it restarts a client that owns its process at most four times in three minutes by default
    (`lib/common/client.js:813`, `:175-196`);
  - given an `Executable`, it spawns the process itself and pipes its stderr line by line into the
    client's output channel (`lib/node/main.js:457-481`, `:145-150`). With
    `TransportKind.stdio` as its transport it appends `--stdio` to argv (`:462-463`);
  - `stop()` allows 2000 ms for `shutdown` and `exit`. For a process it spawned, it checks again
    2000 ms later and kills the whole process tree with `kill -9` (`lib/node/main.js:199-227`,
    `lib/node/processes.js`);
  - it registers every command of a server's `executeCommandProvider` window-wide through
    `vscode.commands.registerCommand`, with no guard (`lib/common/executeCommand.js:83-90`). VS Code
    rejects a duplicate command id _(upstream, not verified here)_;
  - it answers `workspace/configuration` with `workspace.getConfiguration(...).get(section)`
    (`lib/common/configuration.js:79-104`). That value includes the defaults any installed
    extension declares for the section, not only what the user set.
- **How VS Code chooses among formatters** (multi-root research, from VS Code's
  `languageFeatureRegistry.ts` and `formatActionsMultiple.ts`):
  - providers with an equal selector score are ordered newest registration first;
  - `editor.defaultFormatter` is resolved by extension id;
  - with two formatters from the datamitsu extension, the one registered most recently wins;
  - `editor.formatOnSaveMode: "modifications"` or `"modificationsIfAvailable"`,
    `editor.formatOnPaste` and `editor.formatOnType` call range and on-type formatters
    automatically, and an extension's range formatter stands in as its document formatter for a
    file the extension has no document formatter for _(upstream, not verified here)_.
- **Language identifiers come from extensions.** A `language` selector matches only an id some
  installed extension contributes. VS Code ships no `toml` language _(upstream, not verified here;
  reported for the built-in extensions of code-server 4.129.0)_, and the datamitsu extension
  contributes none.
- **Other editors** (multi-root research):
  - Neovim starts a server with `cmd_cwd` or else `root_dir` as its working directory;
  - Helix starts it with the root as the current directory, and gives each request a timeout,
    20 s by default _(upstream)_;
  - both run several servers on one buffer _(upstream)_;
  - Emacs eglot runs one server per project and major mode, so one server per buffer _(upstream)_;
  - Zed adds language servers only through extensions; its model is marked uncertain there.

- A tool reaches such a file only through `{managedConfig:<key>}`. `ResolveManagedConfigPlaceholders`

### 1.10 What binds, and what is context

Binding, from owner-confirmed documents:

- **Granularity §6.1.** Session policy is "emphatically NOT in `config.Config`", and the `lsp`
  Record "is rejected as a home too" for it. An `initializationOptions` override is echoed and
  logged (Layer 3). `lsp: false` stays in the invalidation key knowingly, "for want of a better
  home".
- **Granularity §6.2, §11c.** `repo` granularity never runs on save. A project-wide operation
  without `globs` does not run on save unless `format.tools` opts it in. `datamitsu lsp`'s stderr
  is JSON-L only.
- **Granularity §11.1.** `getMinVersion()` gates anything that ships stable; unstable builds skip
  it.
- **Granularity §12.** The `diagnostics` block of `initializationOptions` stays unoccupied. There is
  no knowledge base of upstream CLI contracts. A field that `vm.ExportTo` would drop silently is
  kept as a rejected tripwire, as `batch` was.
- **CLAUDE.md.** SHA-256 for every download; XXH3-128 through `internal/hashutil` for internal
  fingerprints; settings through `internal/env` and `runtimeconfig.Effective`; nothing new in
  `datamitsuConfigInputs`; managed-config placement, and the preflight "in the runner and the
  language server"; a `configcache.FormatVersion` bump when the encoded config changes;
  `TestContractCompletenessGate`; alpha stage, where breaking changes are allowed and recorded under
  "Product Stage".
- **The code as shipped** is the baseline, which only a decision here changes: the `LspEntry`
  shape, `lessLspByOrderThenName`, and a required `projectTypes`.

Context, not decisions: `revise.txt`, `analysis.md` (the none-ls and efm-langserver analysis) and
the removed WASM parser plan were written by earlier agent runs. This plan cites them only as prior
analysis.

## 3. Architecture options

### 3.1 A — a multiplexing proxy inside `datamitsu lsp`

The editor opens one connection, and datamitsu spawns N child servers behind it. What that requires,
with the evidence that each part is needed:

| Mechanism                    | What the multiplexer must do                                                                                                                                                                                                  | Evidence it is not optional                                                                                           |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Capability merge             | Union list-valued features. Pick one owner for single-answer features (rename, signature help, semantic tokens). Keep `executeCommand` ids from colliding, which C has to do too in VS Code (§7.2).                           | tombi ships its own semantic-tokens legend; ruff declares four command ids (§1.6)                                     |
| Document sync                | Take the richest sync mode from the client, keep a document model, and down-convert it per child                                                                                                                              | tombi wants full sync, ruff incremental (§1.6); today's server keeps only full text (§1.3)                            |
| Routing by document          | Send each `didOpen` to the children that serve its language and root                                                                                                                                                          | needs `languages`, the same field option B needs                                                                      |
| Diagnostics aggregation      | Push: keep one set per (child, uri) and republish the union, since a publish replaces the whole set. Pull: fan out `textDocument/diagnostic` and compose `resultId`s.                                                         | ruff uses pull diagnostics (§1.6)                                                                                     |
| Server-to-client requests    | Forward `workspace/configuration`, `workspace/workspaceFolders`, `window/workDoneProgress/create`, `client/registerCapability` and `workspace/applyEdit` under fresh ids, route the responses back, and remap progress tokens | both servers issue such requests right after `initialized` (§1.6); today's transport cannot receive a response (§1.3) |
| Dynamic registration         | Keep registrations per child, union watched-file globs, and fan `didChangeWatchedFiles` out to the children whose globs match                                                                                                 | both servers register watchers dynamically (§1.6)                                                                     |
| Id remapping                 | Client request ids can pass unchanged per child connection. Ids of server-initiated requests collide across children and need a proxy namespace.                                                                              | —                                                                                                                     |
| `$/cancelRequest` forwarding | Map a client id to every child request it fanned out to, forward the cancel, and answer the client exactly once                                                                                                               | the spec requires exactly one response per request                                                                    |
| Shutdown fan-out             | Send `shutdown` to every child in parallel inside the client's budget, then `exit`, then kill the stragglers                                                                                                                  | vscode-languageclient gives `stop()` 2000 ms in total (transport research §6)                                         |
| Failure isolation            | A child crash must not end the connection, and one hung child must not stall the others or datamitsu's own formatting                                                                                                         | today's server handles one message at a time (§1.3)                                                                   |

What it buys:

- one client entry per editor;
- `order` that is actually enforced;
- a place to put the formatting rule and settings for every editor;
- datamitsu's formatter and a proxied server on one buffer in editors that run a single server per
  buffer (eglot, §1.7).

What it costs:

- a second transport, concurrent and bidirectional with request tracking, next to the one the
  session work is restructuring;
- a document model;
- per-feature merge rules for every capability of LSP 3.17;
- datamitsu becomes the client every server is tested against, while each server was tested
  against real editors.

### 3.2 B — a launcher

datamitsu resolves which servers apply to a root and how to start each one, and each editor
integration starts its own clients:

- the VS Code extension does it itself;
- Neovim and Helix users configure it from the listing. Zed adds servers only through extensions
  (§1.7) and is left out of this plan.

**The launch vehicle.** `datamitsu exec` is not fit for it as it is, for three reasons (§1.4):

1. progress on stdout on a cold store;
2. a supervising parent that forwards no signal;
3. exit codes collapsed to 1.

Fixing `exec` itself would change a general-purpose command. Instead, a dedicated `lsp run` reuses
the shim's exec helper (§5.3).

**What it costs:**

- per-editor wiring;
- rules that datamitsu can only document, not enforce, outside the VS Code extension: the
  formatting removal and the settings.

### 3.3 C — B, with the proxy rules applied on the way

The launcher of B, plus the proxy rules:

- **in VS Code, by the extension's own clients** (D10): they register no formatting, skip command
  ids already taken in the window, apply settings through middleware and pass
  `initializationOptions`;
- **everywhere else, by a relay mode of `lsp run`.** The relay sits between one editor client and
  one server, forwards frames unchanged, and intervenes at exactly three points: formatting
  capabilities, `initializationOptions` and `workspace/configuration`.

One client and one server means no id remapping, no capability merge, no routing and no aggregation.
The frames the relay does not touch pass through byte for byte, and positions are never rewritten.

### 3.4 Comparison

| Criterion                                   | A — multiplexer                        | B — launcher                                      | C — launcher, rules in the extension and the relay                 |
| ------------------------------------------- | -------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------ |
| New datamitsu code                          | transport, document model, merge rules | listing, launcher (reuses the shim's exec helper) | B, a frame relay with three interventions, the rules in TypeScript |
| Editor wiring                               | one client                             | one client per server                             | one client per server                                              |
| Formatting rule                             | enforced for all editors               | VS Code extension; elsewhere user configuration   | enforced: VS Code in the extension, elsewhere once the relay ships |
| `order`                                     | enforced                               | sorts the listing                                 | sorts the listing                                                  |
| Settings from the config                    | yes                                    | VS Code extension only                            | yes, all editors                                                   |
| Processes per server (Unix)                 | 1, plus one shared multiplexer         | 1 (`execve`)                                      | 1 in VS Code (`--no-relay`); 2 elsewhere (relay and server)        |
| Crash isolation                             | shared fate unless built carefully     | per server                                        | per server                                                         |
| Per-message overhead                        | full decode, merge and re-encode       | none after start                                  | none in VS Code; envelope decode and frame copy elsewhere          |
| Editors with one server per buffer (eglot)  | formatter and servers on one buffer    | one server: the user picks it                     | one server: the user picks it                                      |
| Divergence from each server's tested client | highest                                | none                                              | three well-defined points                                          |

### 3.5 Recommendation: C (D1)

Every target editor already multiplexes clients. VS Code keeps one diagnostic collection per client
(diagnostics plan §3.11), and Neovim and Helix attach several servers to a buffer _(upstream)_.
Option A would re-implement that inside a transport that today cannot even receive a response
(§1.3). The two servers probed here already disagree on sync mode, diagnostics model and formatting
registration (§1.6), and each disagreement is a merge rule A would have to own.

What C keeps from A is the one thing datamitsu must own: formatting belongs to `datamitsu fix`, in
every editor. The extension and a one-to-one relay can enforce that without any of A's machinery.

A stays possible later: the relay's framing and interventions are A's leaf components. Reopening it
takes demand, not the mere existence of a single-server editor. eglot is one today (§1.7), and its
users can still start one proxied server from the listing. What they cannot do is run datamitsu's
formatter and a proxied server on the same buffer. A plan for A is written when that gap is asked
for (§8).

## 4. The model

### 4.1 Applicability — which servers apply to a root

| Entry state                                                      | `lsp servers`                                                                                                                                                              | `lsp run <name>`                               |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| `app`, a `projectTypes` name or a `{managedConfig:}` key invalid | load error (S1)                                                                                                                                                            | load error                                     |
| `projectTypes` omitted (D4)                                      | listed for every root                                                                                                                                                      | runs                                           |
| `projectTypes` given, none detected in the root                  | skipped: "no `<type>` in this root"                                                                                                                                        | runs: a launch by name checks no applicability |
| binary app with no build for this host                           | skipped, with the resolver's reason (`BinaryAvailable`)                                                                                                                    | fails before exec                              |
| shell app whose command is not on the composed `PATH`            | skipped: "`<command>` not found on PATH", from an explicit `exec.LookPath`; `ResolveCommandInfo` reports a shell app installed without looking (`binmanager.go:1033-1039`) | fails before exec                              |
| otherwise                                                        | listed, with `installed` true or false (read-only)                                                                                                                         | installs if needed, then becomes the server    |

- **One instance per root.** A server gets one instance per datamitsu root, never one per detected
  project location (§8). A root is the topmost superproject, resolved as the loader resolves it.
- **Detection** runs only when some entry declares `projectTypes`: one gitignore-aware walk through
  `project.Detector.DetectAll`, the marker detection the planner runs. A walk error fails the
  listing and is never reported as a skip; `IsType` would swallow it
  (`internal/project/detector.go:182-189`).
- **The listing never installs.** It uses `ResolveCommandInfo`, which stays read-only.

### 4.2 Capability policy (D2)

| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `documentFormattingProvider`, `documentRangeFormattingProvider`, `documentOnTypeFormattingProvider`, and dynamic registrations of `textDocument/formatting`, `rangeFormatting`, `rangesFormatting` and `onTypeFormatting` | removed                                                | `datamitsu fix` is the formatter of record. | Diagnostics, push or pull                                                                                                                                                                                                 | kept                                                   | This is the main reason to run a server. datamitsu's own diagnostics (diagnostics plan) arrive on a different client, and the editor shows both.                                                                                                                                                                                                                                                                                                                             |
| Code actions, including `source.*` kinds                                                                                                                                                                                  | kept                                                   | Not formatting. | `executeCommandProvider`                                                                                                                                                                                                  | kept; in VS Code an id already taken is skipped (§7.2) | Command-backed code actions need it.                                                                                                                                                                                                                                                                                                                                                                                                                                         |

**What removal costs.** Removing a proxy's formatting does not mean datamitsu formats that document
on save. datamitsu's own server leaves it unformatted when:

- the author vetoes the operation (`lsp: false`) or the user does (`format.tools[name] = false`)
  (granularity §6.1);
- `format.widenTo: "target"` leaves out the unit operation that formats it;
- the operation has `repo` granularity (granularity §6.2), or is project-wide with no `globs` and
  not opted in (granularity §11c). The pinned wrapper's `golangci-lint fmt` is such an operation:
  `args: ["fmt"]`, `scope: "per-project"`, no globs
  (`node_modules/@shibanet0/datamitsu-config/datamitsu.config.base.js:11321-11330`). With a proxied
  gopls, Go files are then formatted by neither side on save;
- the watchdog stops the chain between priority groups.

The document is then formatted by the next `datamitsu fix`, in the hook or in CI, not by the next
save. The remedy is on datamitsu's side: `globs` or `{files}` from the author (wrapper HEAD already
moves `golangci-lint-fmt` to `{files}`), or `format.tools` from the user. The documentation says so
next to each editor's recipe.

**Where the rule is applied.**

- **S2 and S3:** the documentation shows each editor's own knob for turning a server's formatting
  off.
- **VS Code (S5):** the extension wraps the client's formatting features, obtained through
  `client.getFeature` (a public API of vscode-languageclient 10.1.1), so they register nothing,
  statically or dynamically (D10).
- **Other editors (S4):** the relay removes the static capabilities from the `initialize` result,
  and drops formatting registrations from `client/registerCapability`: ruff's is dynamic (§1.6). A
  request whose registrations are all dropped is answered by the relay and never reaches the
  editor, along with any later `unregisterCapability` for the dropped ids.

### 4.3 What `order` means (D5)

The shipped field sorts entries: lower `order` first, ties by entry name
(`lessLspByOrderThenName`). This plan gives it that meaning and no other:

- the listing is sorted by it;
- the Neovim and Helix recipes list entries in listing order. Helix ranks servers for single-answer
  features by its `language-servers` order _(upstream)_.

VS Code gets no start-order logic. It merges list-valued features such as completion, hover and
references across providers. For the rest, which provider answers follows registration order, and
lazy start, one-at-a-time installs and crash restarts all move that _(upstream)_. The extension
cannot hold such a precedence, so it does not offer one.

### 4.4 Settings and `initializationOptions` (D6)

If D6 is accepted, the entry gains `settings` (sections keyed by name) and `initializationOptions`.

**How they reach the server.**

- **VS Code (S5).** `initializationOptions` is passed as the client option. `settings` is applied by
  `middleware.workspace.configuration`. For each requested section, a value the user set (global,
  workspace or folder, read with `inspect()`) wins over the entry's, and the entry's wins over
  defaults. The stock answer uses `get()`, which carries the defaults other extensions declare
  (§1.7). Without the middleware, an installed Go extension's `gopls.*` defaults would override a
  team's settings.
- **Other editors (S4).** The relay deep-merges `initializationOptions` under what the client sent.
  It merges `settings[section]` under the client's answer to `workspace/configuration`, tracking the
  request id. Neovim and Helix answer with the user's own table, so there "the client wins" means
  what it says.
- **Scope.** Servers that read settings through `workspace/configuration` or
  `initializationOptions`. A server that reads only `workspace/didChangeConfiguration` payloads is
  not reached. The reference says which model each wrapper entry's server uses.
- **Logged.** Every injection is reported: one JSON-L `log` event per `initialize` and per
  `workspace/configuration` answer, naming the injected keys (relay), and the same line in the
  client's output channel (VS Code). Granularity §6.1's Layer 3 asks this of an override.

**Against granularity §6.1.** §6.1 keeps session policy out of `config.Config` for two reasons: it
would reset the shared cache, and the `lsp` Record has no room for a policy scalar. S1 takes `Lsp`
out of the invalidation key (§4.8), which removes the first. The second is about datamitsu's own
editor policy, a scalar. Per-server `settings` are a different kind of thing: shared server
configuration, like the tool configs datamitsu already renders. They can still carry editor
preference, though: inlay hints, completion behaviour, formatting options. This plan proposes a
criterion: `settings` hold only what changes what a server computes or reports — build flags,
analyses, schema associations — never interaction preferences. The reference states it with
examples; no validator can enforce it. D6 asks the owner to confirm this reading of §6.1, or to
treat D6 as an amendment to it.

`datamitsu lsp`'s own `initializationOptions` are untouched, and their `diagnostics` block stays
reserved for the diagnostics plan (`internal/lsp/policy.go:98-99`; granularity §12).

### 4.7 Provisioning: lazy

`init` does not install an app referenced only by a proxy entry. That is not a proxy-specific rule:
`init` does not install a binary tool app either unless it is `required` (§1.5), and ruff and tombi
install on the first `lint` or `fix`. A proxy's app installs on the first `lsp run`, or, in VS Code,
through `datamitsu install <app>` just before its client starts (§5.6). Two escape hatches exist:
`required: true` on the app, or `datamitsu install <app>`.

The generated Dockerfile and the store bundles do carry every app (§1.5). The wrapper's first
entries (tombi, ruff) add nothing there, since both apps already exist. A server that is not a tool
app — gopls, rust-analyzer, typescript-language-server — would add its size to every CI image (D14).

### 4.8 Cache

- **The execution cache.** `calculateInvalidationKey` hashes the config with `Lsp` cleared. This
  follows granularity §6.1's reasoning; §6.1 itself was about the `lsp: false` veto. No entry
  changes what a tool reports, and with D6's `settings` an entry becomes something a team tunes
  often. It moves no existing key (§1.2).
- **`lsp: false` stays in the key.** §6.1 moves the veto out only if its edits stop being
  maintainer-frequency, and this plan does not change how often it is edited.
- **Server apps.** Adding or bumping a server app in `apps` still resets the cache once, like any
  app bump. That is accepted.
- **The config-eval cache.** S1 bumps `configcache.FormatVersion`, because `LspEntry` changes shape.
  S4 bumps it again if it is the stage that adds `settings` (§6). If the diagnostics plan's Stage 4
  lands in the same release as S1, the two share one bump.
- **The diagnostics plan.** Once S1 lands, that plan's cache-reset argument for removing `derived`
  (its §3.12) no longer applies. Its other reasons stand.

### 4.9 Relationship to `derived`

The diagnostics plan recommends removing `derived`: diagnostics derive from lint operations, and
`derived` has nothing left to declare (its §3.12, D6). This plan relies on none of `derived`. If D6
there is accepted:

- `type` stays, with the single value `"proxy"`, so the schema remains open without a migration;
- `LspEntry.Tool` keeps the proxy meaning D9 gives it. Without D9 it stays as a field a proxy may
  not carry: a load error, rather than a key `vm.ExportTo` would silently drop (granularity §12);
- the facet-rule comment in `validate.go` stops anticipating "a future lsp binding".

Proxied diagnostics and datamitsu's own diagnostics never share a client, and no one deduplicates
across them (§8).

### 4.10 Tool configs datamitsu renders (D9)

A proxied server finds its configuration the way it does on the command line: by walking up from
the document or the root. It never finds `.datamitsu/configs/` (§1.8). Once a server's config file
becomes internal, the proxied server and `datamitsu lint` read different rules, and the editor shows
the two contradicting each other on the same file, with no error anywhere.

The recommended answer:

- A proxy may name one `tool`. Its `args` may then contain `{managedConfig:<key>}` for a key whose
  `tools` list that tool: the association rule of tool operations (`managed_config_eject.go:282-288`).
  Ejecting the tool then moves the file its server reads as well.
- `ResolveManagedConfigPlaceholders` resolves proxy entries after the chain, as it does operations,
  and records the keys on the entry (`ManagedConfigRefs`).
- A key with `project` scope, whose path resolves under `{cwd}`, is a load error: one instance per
  root has no project directory. Ejectable and `git-root` keys resolve under `{root}`.
- `lsp run` expands the resolved `{root}` prefix to the datamitsu root and runs
  `managedconfig.CheckConfigFiles` for the entry's keys before exec. A missing or stale render fails
  before exec with the preflight's "run `datamitsu init`" message.

No other placeholder is accepted in `args` (§5.2).

### 5.1 Configuration

### 5.3 `datamitsu lsp run <name> [--no-relay] [-- extra args]` (S2; relay from S4)

1. **Mode.** It runs under `lsp`'s JSON-L quiet mode (`cmd/lsp.go:39-40`). Nothing reaches stdout
   before the server does. Its stderr is JSON-L until the server starts, then the server's own
   stream. A `phase` event with status `done` marks the hand-over. In direct mode it is the last
   line datamitsu writes; in relay mode the relay's later `log` events (§4.4) are interleaved with
   the server's lines, one whole line at a time.
2. **Root.**
   - _Direct mode_ (S2, and `--no-relay` later): the root comes from the launch directory. It
     records that directory, resolves the root with the loader's resolver, changes to the root to
     load the config, and changes back, so the server keeps the directory the editor chose. The
     editor must therefore start it inside the repository: Neovim through `cmd_cwd` or
     `root_markers`, Helix through its root. Outside a repository it fails before exec.
   - _Relay mode_ (S4): the relay reads the client's `initialize` first and takes the root from
     `workspaceFolders[0]`, `rootUri`, `rootPath`, then the launch directory. That is the session
     work's precedence, with its URI-to-path and canonicalization helpers. The client is already
     waiting for the reply while the relay loads, installs and spawns.
3. **Resolving.** It looks up the entry and rejects an unknown name before anything starts, listing
   the known names. It checks no applicability (§4.1). It calls `GetCommandInfo(app)`, which
   installs on first use and composes the environment and the dependency `PATH`. With D9 it runs
   `CheckConfigFiles` for the entry's keys (§4.10).
4. **The command line.** argv is the app's command and args, then the entry's `args` (with `{root}`
   expanded under D9), then the extra args. argv[0] follows the shim's `execArgv0` rule, with the
   app name standing in for the typed name. A bare command (a shell app, a system-mode `java`) is
   resolved with `exec.LookPath` against the composed environment's `PATH`, as the shim does.
   Global config-chain flags are not repeated here; the listing puts them in `command`.
5. **Launching.**
   - _Direct mode_: on Unix, `syscall.Exec`. The shim's exec helper moves out of `package shim` into
     a small package both use, and is injected so unit tests can stub it, as `Dispatcher.Exec`
     allows today. On Windows, a child with inherited stdio whose exit code it adopts, like the shim
     (D16).
   - _Relay mode_: §5.5. From S4 the relay is the default; `--no-relay` keeps direct mode, and the
     VS Code extension uses it (D10).
6. **Signals before exec.** SIGTERM or SIGINT during an install lets the install finish, bounded by
   the install timeout, then exits without starting the server. A pnpm or uv install killed midway
   can leave a directory the next health check accepts (transport research §3). Outside an install
   it exits at once.
7. **Failure before exec.** It emits one JSON-L `error` event and exits with a dedicated code
   through `CodedError`, chosen in S2 and frozen by a golden, so a client can tell "could not start"
   from a server crash. The editor sees the process exit before `initialize`.

### 5.4 `datamitsu lsp servers [--json]` (S3)

It is read-only. With `--json` it keeps `lsp`'s quiet mode: JSON-L on stderr, only the document on
stdout. Outside quiet mode a config's `console.log` would reach stdout ahead of the document (§1.4).
Without `--json` it prints a table for a terminal — name, app@version, languages, and status or
skip reason — and switches to console mode for that.

```json
{
  "schemaVersion": 1,
  "root": "/home/u/repo",
  "watch": [
    "/home/u/repo/datamitsu.config.ts",
    "/home/u/repo/.git/HEAD",
    "/home/u/repo/pnpm-lock.yaml"
  ],
  "servers": [
    {
      "name": "ruff",
      "app": "ruff",
      "appKind": "binary",
      "version": "0.16.4",
      "pinned": true,
      "installed": true,
      "languages": ["python"],
      "projectTypes": ["python-package"],
      "order": 0,
      "command": [
        "/usr/local/bin/datamitsu",
        "--before-config",
        "/home/u/repo/base.js",
        "lsp",
        "run",
        "ruff"
      ],
      "installCommand": [
        "/usr/local/bin/datamitsu",
        "--before-config",
        "/home/u/repo/base.js",
        "install",
        "ruff"
      ],
      "fingerprint": "<xxh3-128 hex>"
    }
  ],
  "skipped": [
    { "name": "rust-analyzer", "reason": "no rust-project in this root", "languages": ["rust"] }
  ]
}
```

- **`schemaVersion` 1** is experimental until S5, its first consumer, ships.
- **`command`** starts with the resolved executable, followed by the global config-chain flags this
  listing was invoked with, made absolute by `configChainArgs` (`cmd/source.go:453-466`), and by
  `--binary-command` when it was given, so `facts().binaryCommand` matches. The environment cannot
  travel in argv. A listing produced through `pnpm datamitsu` has `DATAMITSU_PACKAGE_NAME` set and
  the editor's environment usually does not, which costs one config-eval miss per distinct
  environment, not one per start.
- **`installCommand`** is the same prefix with `install <app>`.
- **`watch`** is the config watch set: `sourcefarm.WatchPaths(root, ConfigChainFiles())`, or
  `ConfigWatchPaths` for an explicit chain. The session work fingerprints the same set (§1.9).
- **`fingerprint`** is XXH3-128 through `internal/hashutil` over the resolved launch identity: the
  entry, the full `command`, and the `ResolveCommandInfo` result (command path, args, env, dependency
  `PATH`). Store paths are content-addressed, so the result already moves with the runtime, with
  the pnpm runtime of a Node or Bun app, and with the `dependsOn` closure. It is encoded with
  `json.Marshal`, whose map keys are sorted, so a config-eval hit and a fresh evaluation agree.
  `installed` is not part of it. It is never compared with an external value, so XXH3 is the right
  hash.
- **Skipped entries** carry a reason and their `languages`. They are never dropped silently.
- With D6, each server also carries `settings` and `initializationOptions` for the VS Code
  extension (§4.4).

### 5.5 The relay (S4)

- **Root.** From `initialize` (§5.3, step 2). The relay reads that one message before it spawns the
  server, then forwards it.
- **Framing.** It speaks Content-Length frames in both directions. For each message it decodes only
  the envelope: `id`, `method`, and the presence of `result` or `error`. Untouched frames are
  forwarded as the original bytes.
- **Interventions:** the formatting removal (§4.2) and, with D6, the settings merge with its log
  events (§4.4). It has no other behaviour.
- **Process.** SIGTERM and SIGINT are forwarded to the server. The relay exits when the server
  exits, with the server's code. Stdin EOF closes the server's stdin. The server's stderr passes
  through, line by line, after the relay's hand-over event.
- **Windows.** There is no SIGTERM. The relay closes the server's stdin when its own stdin reaches
  EOF, and never outlives the server.
- **Settings.** The relay has none in S4. Any it gains later goes through `internal/env` and
  `runtimeconfig.Effective`, per the environment-variable and introspection policies.

### 5.6 VS Code extension (S5)

- **Settings.**
  - `datamitsu.servers.enabled` (boolean, default `false`; D7);
  - `datamitsu.servers.exclude` (entry names).
- **Discovery.** After datamitsu's own client starts, the extension runs `<binary> lsp servers --json`
  with the root as `cwd`. When the binary has no `lsp servers` (an older `datamitsu.path` or bundled
  binary) or the listing fails, it shows one warning and starts no proxies. datamitsu's own client is
  unaffected.
- **Installing, outside the client lifecycle.** For an entry with `installed: false`, before its
  first client starts, the extension runs `installCommand` as a process of its own, with
  `--log-format jsonl`, and attaches `JsonlProgress` to its stderr. Installs run one at a time per
  window, with a timeout on the wait. Stopping a client ends its process, and for an `Executable`
  vscode-languageclient kills the whole tree (§1.7), so an install run inside a client can be cut
  short by a reload or a restart; one run outside it cannot.
- **One `LanguageClient` per listed entry and root:**
  - `serverOptions`: a function that spawns `command` plus `--no-relay` and returns a `StreamInfo`,
    as `spawnServer` does for datamitsu's own server (`extension.ts:108-150`). `transport` stays
    unset: `TransportKind.stdio` would append `--stdio`, which `lsp run` rejects (§1.7). stderr is
    read as JSON-L up to the hand-over event, then passed line by line to the client's output
    channel;
  - `workspaceFolder`: the workspace folder that maps to the root;
  - `documentSelector`: `{scheme: "file", language, pattern: RelativePattern(base, "**/*")}` for
    each language. `base` is each workspace folder inside the root, spelled as the folder was
    opened: a canonical path does not match a folder opened through a symlink (§1.9). When a folder
    contains the root instead, `base` is the root spelled under that folder (D12);
  - `errorHandler`: on the pre-exec exit code (§5.3) it returns `DoNotRestart` and shows the error
    event's message.
- **The proxy rules (D10).**
  - The client's formatting features are wrapped so they register nothing (§4.2).
  - The `executeCommand` feature is wrapped so that an id already registered in the window is
    skipped, with one warning (§7.2).
  - With D6, `initializationOptions` and the `settings` middleware of §4.4.
- **Languages.** An entry's language id that VS Code does not know (`vscode.languages.getLanguages()`)
  is reported once per entry, never dropped silently. The extension contributes the `toml` id (D3).
- **Start.** Lazily, on the first matching open document.
- **Reload (D11).** The extension watches the `watch` paths through `createFileSystemWatcher`,
  debounces, and re-lists. VS Code excludes `node_modules` from watching by default, so a wrapper
  bump is seen through `pnpm-lock.yaml`. It also re-lists, rate-limited, on the first open of a
  document in a skipped entry's language. Each client is stopped, started or left by `fingerprint`.
  A failed listing keeps the running clients and shows one warning.

## 7. Risks

1. **Duplicate servers in VS Code.**
   - Many users already run a language extension that starts its own copy of the same server: the
     Go extension starts gopls.
   - Two copies mean doubled diagnostics, hovers and memory.
   - Detecting them would need a table of extension ids per server, which this plan refuses (§8).
   - Mitigation: opt-in (D7).
2. **Command id collisions in VS Code.**
   - vscode-languageclient registers every command of `executeCommandProvider` window-wide (§1.7),
     and ruff declares four `ruff.*` ids.
   - Two datamitsu clients of one server (two roots in one window), or a datamitsu client next to
     the Ruff extension's own, collide, and the second client fails to start.
   - Mitigation (S5): an id already registered in the window is skipped, with one warning. That
     client's command-backed actions for the id then do not work.
   - Rejected: dropping `executeCommand` altogether (it loses every command-backed action), and
     rewriting ids in the relay (a fourth intervention, touching every `Command` a server sends).
3. **Language identifiers.**
   - VS Code knows only the ids an installed extension contributes, and has no `toml` (§1.7). The
     extensions that do contribute it usually start their own tombi or taplo, which is risk 1.
   - Neovim, Helix and VS Code do not always agree either: for example, how `go.mod` is named
     _(upstream)_.
   - Mitigation: the extension reports ids it does not know and contributes `toml` (D3); the Neovim
     and Helix recipes show the known differences.
4. **Pinned is not offline, and not inert.**
   - A server can download schemas or toolchains and can execute project code (§4.5).
   - gopls type-checks with the host `go` (§1.5): the server is pinned, the toolchain it drives is
     not.
   - The hash policy covers the server artefact only. The documentation says so, and the entry's
     `args` can carry offline flags.
5. **Formatting leaks through code actions.**
   - Before S4, and outside VS Code, removal depends on each editor's configuration.
   - After S4 and S5, a server can still format through a code action on save (`source.fixAll`,
     `source.organizeImports`) that the user enabled in the editor. Stripping code actions would
     remove legitimate fixes, so the documentation names the setting instead.
6. **Races in the store.**
   - A runtime app installs in place, and a failed install deletes its directory. There is no
     cross-process lock (multi-root research §4).
   - The VS Code extension installs outside the client lifecycle, one at a time per window.
   - Still unmitigated: a proxy install at the same moment as datamitsu's own formatting server
     installing the same runtime's apps on a fresh clone, or as another window or a terminal. S5
     records a backlog item for a cross-process install lock. A test cannot prove the race absent.
7. **Store operations while servers run.**
   - A server is the first long-lived holder of store files.
   - On Windows, a running server's `.exe` blocks `datamitsu store clear` and a reinstall. On Unix, a
     Node server that loads files lazily breaks if its install is removed under it.
   - A future store GC (backlog `store-keeps-every-superseded-install-forever`) must not collect an
     install a running server holds.
8. **Nested roots.** An unregistered nested repository sits under two roots' selectors, and its
   documents reach both roots' servers. Routing to the deepest root is multi-root work (diagnostics
   plan §3.11 names the same gap).
9. **Windows (D16).**
   - There is no `execve`, so a datamitsu parent stays alive, and there is no job object: the shim
     has none either (`exec_windows.go`).
   - A parent the editor kills leaves the server running until its stdin reaches EOF, which happens
     when the editor closes the pipe (transport research §2).
   - CI runs only on Linux (`.github/workflows/pr-checks.yml`), so the Windows path ships untested.
10. **Start latency.**
    - The first open on a fresh machine downloads the server.
    - `lsp run` loads the config every time. `config show` takes about 21 ms on a config-eval cache
      hit and about 59 ms on a miss (config-load research, measured in this repository). A server
      start is expected to pay the same; it has not been measured. `lsp run` walks nothing.
    - The listing walks the repository once, when an entry declares `projectTypes`, at each
      extension start and each re-list. Walk cost grows with the tree; S3 measures it (§6).
11. **No formatter on save.** Removing a proxy's formatting can leave a language unformatted on save
    by either side (§4.2). The documentation names the remedy with each recipe.

## 8. Non-goals

Explicit refusals, not deferred versions. Decisions already made in §4 and §5 are not repeated here.

- **No multiplexer in this plan.** It is reopened only on demand (§3.5), and then as a plan of its
  own built on the relay's components.
- **No capability merging, no diagnostics aggregation, no deduplication across sources.** Where
  golangci-lint and gopls report the same finding, the switch is per user: on datamitsu's side the
  diagnostics plan's `datamitsu.diagnostics.tools`, on the server's side its own settings (through
  D6 or the editor). `lsp: false` is the wrong lever: it vetoes the operation in every editor.
- **No server catalogue.** datamitsu ships no table of known servers, default languages per project
  type or conflicting editor extensions. Entries are written by config authors, in the wrapper or
  the project, which follows the granularity plan's "no knowledge base of upstream CLI contracts".
  The one language id the extension contributes (D3) is editor knowledge, not a server table.
- **No globs on a proxy.** The shipped shape has no globs field, and this plan adds none: `languages`
  routes documents, `projectTypes` selects roots, and which paths a server analyses is that server's
  own concern.
- **No instance per project location.** A monorepo with several Python packages gets one server
  instance, rooted at the datamitsu root. Per-location instances multiply memory, and servers have
  their own multi-project configuration.
- **No trust store.** datamitsu adds no allowlist of its own. It relies on the editor's trust and
  documents the rest.
- **No proxied traffic through `datamitsu lsp`.** The formatting server and proxied servers stay
  separate processes and separate clients.
- **No inspector or showcase surface** for language servers in this plan.

## 9. Verification

End-to-end checks that must pass before the work is considered done.

1. **Validation bites.**
   - An entry with `app: "gopls"` and no such app fails the load, naming the entry.
   - So does `projectTypes: ["golang"]` against the wrapper.
2. **The cache is untouched.** Add, edit and remove an `lsp` entry between two `datamitsu lint`
   runs. `calculateInvalidationKey` is unchanged, and every per-file entry and unit verdict that does
   not cover the edited config file still hits.
3. **Stdout purity.**
   - Setup: an empty `DATAMITSU_CACHE_DIR` and a server app that must be downloaded.
   - The first bytes on stdout of `datamitsu lsp run <name>` are `Content-Length:`.
   - Every stderr line before the hand-over event parses as JSON-L. After it, stderr is the
     server's.
4. **Process.**
   - _Direct mode, Unix (S2, and `--no-relay`):_ the pid the editor spawned is the server's; SIGTERM
     reaches the server; `exit` before `shutdown` yields exit 1 from the process the editor started.
   - _Relay (S4):_ SIGTERM and SIGINT reach the server; its exit code is the relay's; stdin EOF
     closes the server's stdin; the relay exits when the server exits.
   - _Before exec:_ SIGTERM during an install lets it finish, and the process exits with the
     pre-exec code.
5. **Listing.**
   - In a repository with `python-package` and no `rust-project`, `ruff` is listed and a
     `rust-analyzer` entry is skipped with its reason.
   - `jq '.servers[].name'` follows `order`, then name.
   - A config layer that calls `console.log` does not break `jq`.
6. **The formatting rule (S4 relay, S5 extension).**
   - Against ruff 0.16.4, no formatting registration of any kind reaches the client or VS Code,
     while its watcher registration arrives unchanged.
   - Against tombi 1.5.0, the `initialize` result lacks `documentFormattingProvider`.
   - ruff's range formatting is not offered.
7. **VS Code (S5).**
   - With tombi proxied and `datamitsu.servers.enabled`, Format Document on a `.toml` emits
     datamitsu's `tool_run` for the tombi fix. It still does after ten forced restarts of the tombi
     client.
   - With `editor.formatOnSaveMode: "modifications"` and `editor.formatOnPaste` on, no proxy formats
     anything.
   - In a clean profile where the datamitsu extension is the only extension, the tombi client
     receives `didOpen` for a `.toml` file.
   - A workspace opened through a symlink starts its proxies.
   - An untrusted workspace starts no proxy.
   - Two roots in one window, both proxying ruff: both clients start, and the second logs the command
     ids it skipped.
8. **Reload (S5).** With format-on-save off and no format request:
   - removing an `lsp` entry and saving the config stops its client, and the other clients keep
     their process ids;
   - `git switch` to a branch whose config lacks the entry does the same;
   - adding a `pyproject.toml` and then opening a Python file starts the ruff client.
9. **No formatter after removal.** With the pinned wrapper (glob-less `golangci-lint fmt`) and a
   gopls proxy declared as a shell app in a local layer, saving an unformatted `.go` file leaves it
   unformatted, and the Go recipe names the remedy.
10. **Contract.**
    - `go test ./test/cli/ -count=2` is byte-stable.
    - `TestContractCompletenessGate` passes with `lsp run`, `lsp servers`, and `lsp` itself as a
      runnable parent.
    - `go test -race ./...` is clean.

## 10. Decisions for the owner

**D1. Architecture.**

- **Recommended:** C. A launcher now; the proxy rules applied in the VS Code extension (D10) and by a
  one-to-one relay for other editors; no multiplexer (§3.5).
- **Alternative A — multiplexer:**
  - one editor entry, enforced precedence, and datamitsu's formatter plus servers on one buffer in
    single-server editors;
  - costs a second concurrent bidirectional transport, a document model and per-capability merge
    rules (§3.1);
  - makes datamitsu the client every server is effectively tested against.
- **Alternative B — pure launcher, no relay:**
  - the smallest code;
  - the formatting rule and config-side settings exist only in the VS Code extension; other editors
    get documentation.

**D2. Formatting from proxied servers.**

- **Recommended:** always removed: document, range and on-type, static and dynamic (§4.2). This
  accepts that a language whose fix operations the editor policy leaves out is formatted on save by
  neither side. The remedy is `globs` or `{files}` from the author, or `format.tools` from the user,
  documented with each recipe.
- **Alternative — keep range and on-type formatting:**
  - Format Selection keeps working;
  - in VS Code they then run on save under `formatOnSaveMode: "modifications"`, on paste and on
    typing, and stand in for datamitsu's document formatter when its client is down (§1.7). Only
    documented settings would guard against that.
- **Alternative — remove only where datamitsu's own policy would run a fix for the document:**
  - no language is left unformatted on save;
  - the relay does not know the editor policy, which lives in datamitsu's own client's
    `initializationOptions`; a static capability cannot vary per document; and the editor's bytes
    would diverge from `datamitsu fix` in hooks and CI.
- **Alternative — per-entry opt-in (`formatting: true`):**
  - lets a team keep a server's formatter;
  - brings back a second formatter under datamitsu's extension id, which VS Code resolves by
    registration recency;
  - lets editor output diverge from `datamitsu fix` in hooks and CI.

**D3. How documents reach a server.**

- **Recommended:** a required `languages` field of LSP language identifiers, which is what every
  client already routes on. In VS Code the extension reports ids the editor does not know, and
  contributes the `toml` id, which VS Code lacks and the wrapper's first entry needs (§1.7).
- **Alternative — `filePatterns` per entry, used only for routing where an id is unknown:**
  - config-driven, with no id in the extension;
  - VS Code would then send the document as `plaintext`, and whether a server accepts that is up to
    each server _(upstream)_.
- **Alternative — no field; each editor maps servers to languages:**
  - keeps the schema as shipped;
  - the VS Code extension could not build a selector without a table of its own (§8);
  - Neovim and Helix users would type the mapping by hand.
- **Rejected — globs:** path scoping is the server's own concern, and `languages` plus
  `projectTypes` already route documents and select roots (§8).

**D4. `projectTypes` on a proxy.**

- **Recommended:** optional. An omitted list means every root, as a tool without `projectTypes`
  applies everywhere (`planner.go:788-805`). A TOML or YAML server has no natural project type.
- **Alternative — keep it required and non-empty, as shipped:**
  - no change to the wrapper gate;
  - every language-wide server needs an invented project type whose markers are, for example,
    `**/*.toml`.
- **Either way,** names are validated (§5.2).

**D5. What `order` means.**

- **Recommended:** it sorts the listing, and through it the Neovim and Helix recipes. VS Code gets
  no start-order logic (§4.3).
- **Alternative — remove the field:** free at the alpha stage; the recipes lose a declared order.
- **Alternative — start order in VS Code:** best effort only; lazy start, one-at-a-time installs and
  crash restarts reorder registrations.
- **Alternative — enforce it in VS Code** with one provider of the extension's own that dispatches
  single-answer requests by precedence: a small TypeScript multiplexer, for one editor only.

**D6. Server settings in the config.**

- **Recommended:** yes. `settings` and `initializationOptions` live on the entry, within the
  documented criterion: what a server computes or reports, never interaction preferences. Values
  the user set in the editor win, and every injection is logged (§4.4). This reads granularity §6.1
  as not covering per-server settings once `Lsp` leaves the cache key; confirm the reading, or treat
  D6 as an amendment to §6.1.
- **Alternative — editor-side only:**
  - no new fields;
  - every developer configures every server in every editor, and teams cannot share
    `buildFlags`-style settings.
- **Alternative — the config wins over the user:** enforces team settings, but overrides a local
  preference the user set on purpose.

**D7. VS Code default.**

- **Recommended:** opt-in, with `datamitsu.servers.enabled` defaulting to `false`. The common setup
  already has a language extension running the same server (§7.1).
- **Alternative — on by default:**
  - the pinned toolchain without a setting;
  - duplicated servers for most users on first install, and no way to detect them without a table of
    extensions.

**D8. Command names.**

- **Recommended:** `datamitsu lsp run <name>` and `datamitsu lsp servers [--json]`. They sit under
  `lsp`, which already means "the editor's entry point"; `lsp run` keeps its forced JSON-L mode up
  to the hand-over, and `lsp servers --json` keeps it throughout. `lsp` becomes a runnable parent,
  so S2 extends `TestContractCompletenessGate` to keep its registered test (§6).
- **Alternative — `datamitsu exec --lsp <name>`:** reuses a familiar verb, but mixes an editor
  protocol concern into a general command whose stdout behaviour differs (§1.4).
- **Alternative — `datamitsu config lsp`:** reads as introspection. But `config` subcommands
  describe the configuration, while `lsp servers` answers what applies to one root and feeds an
  editor's launch contract.
- **Alternative — top-level names outside `lsp`:** the gate stays untouched, at the cost of a
  second editor entry point in the command tree.
- **Either way,** the goldens freeze the names at S2 and S3.

**D9. Tool configs datamitsu renders.**

- **Recommended:** `{managedConfig:<key>}` in a proxy's `args`, licensed by an optional `tool` on the
  proxy, resolved after the chain, with `project`-scoped keys rejected and the preflight in `lsp run`
  (§4.10). Consequences: "a proxy carries no `tool`" becomes "a proxy's `tool` names a configured
  tool" (§5.2), and `LspEntry.Tool` outlives `derived` (§4.9).
- **Alternative — license through the managed config's own `tools` naming the entry:** no new field
  on the entry, but `tools` names tools today and an unknown name there is a load error, so it would
  need a second namespace.
- **Alternative — no placeholders:** the smallest change. Proxied servers then read only repository
  copies, so once a server's config is internal (13 tool-only configs are at wrapper HEAD, §1.8),
  the editor and `datamitsu lint` disagree without an error. That becomes a known limit in §7 and in
  the reference.

**D10. Where VS Code applies the proxy rules.**

- **Recommended:** in the extension. It wraps the client's formatting features, skips
  `executeCommand` ids already taken in the window, applies `settings` through middleware and passes
  `initializationOptions`, and launches `lsp run --no-relay`. S5 then depends on S3, not S4, and
  each server is one process. The relay stays the default of `lsp run` for every other editor.
  The cost: the formatting rule exists in Go and in TypeScript, each with its own tests.
- **Alternative — the relay in VS Code too:**
  - one implementation of the rules;
  - VS Code waits for S4, runs two processes per server, and its `workspace/configuration` answers
    carry other extensions' defaults, which the relay cannot tell from the user's values (§4.4).
- **Alternative — no relay anywhere (D1's B):** VS Code as recommended; other editors by
  documentation only.

**D11. What makes VS Code re-list after a config change.**

- **Recommended:** the extension owns the trigger. It watches the listing's `watch` paths and
  re-lists on a change, and on the first open of a skipped entry's language (§4.6).
- **Alternative — a typed signal from the session work** (a `uievent` type of its own, or a
  `datamitsu/configurationChanged` notification carrying a fingerprint):
  - one fingerprint for both clients;
  - the session work reloads only when a format request arrives (§1.9), so with format-on-save off
    the signal never comes, and the dependency crosses two plans in flight.
- **Rejected — matching the "configuration reloaded" log text:** a human-readable message is not a
  contract.

**D12. Trust.**

- **Recommended:** proxies inherit `datamitsu lsp`'s boundary. The root may be an ancestor of the
  trusted folder, where datamitsu already evaluates config and runs tools. Selectors cover only the
  workspace folders inside the root (§4.5, §5.6), so no document outside a trusted folder reaches a
  proxy; the server process itself still works over the whole root.
- **Alternative — start proxies only when the root equals or lies inside a trusted folder:**
  - a server never runs over code outside the trusted folder;
  - opening one package of a monorepo, the common case, gets no proxies at all, while
    `datamitsu lsp`'s own boundary stays wider.

**D13. Where `lsp run` takes its root.**

- **Recommended:** the launch directory in direct mode (S2, and VS Code's `--no-relay`, which spawns
  with `cwd` set to the root); `initialize` in relay mode (S4), with the session work's precedence
  and helpers (§5.3).
- **Alternative — always the launch directory:** the simplest. Neovim without a root starts the
  server in its own working directory, which may be another repository or none.
- **Alternative — always `initialize`:** every mode would have to read a message before exec, which
  gives up the one-process `execve` identity.

**D14. Server apps in CI images.**

- **Recommended:** accept the current behaviour for now. The wrapper's first entries use apps the
  images already carry (§4.7). When W proposes a server that is not a tool app, measure the image
  growth and decide then.
- **Alternative — leave out of `dockerfile.BuildPlan` the apps referenced only by `lsp` entries,
  unless `required`, with a test:**
  - images stay lean;
  - the images stop matching `init --all`, and an editor seeded from a store bundle downloads its
    servers.

**D15. Shell apps as servers.**

- **Recommended:** allowed, and reported with `pinned: false` in the listing and the table.
  rust-analyzer is best matched to the host's rustup toolchain _(upstream)_.
- **Alternative — reject shell apps:** every proxied server is pinned; rust-analyzer and anything
  else tied to a host toolchain cannot be declared.

**D16. Windows.**

- **Recommended:** a child with inherited stdio that ends with its stdin, and no job object, as in
  the shim. The orphan window, until the editor closes the pipe, is documented. A backlog item
  records the job object together with a Windows CI job.
- **Alternative — a job object in S2, with a `windows-latest` CI job covering at least `lsp run`
  and the shim:**
  - no orphans;
  - new Windows-only code, in a repository whose CI runs only on Linux today.
